# Changelog

All notable changes to this project are documented here, starting from this release. Format loosely follows [Keep a Changelog](https://keepachangelog.com/).

## [Unreleased]

### Changed

- All Django settings renamed to a unified `WF_` prefix: `WORKFLOW_USERS_GROUPS` → `WF_USERS_GROUPS`, `WORKFLOW_ADMIN` → `WF_ADMIN`, `WORKFLOW_ADMIN_GROUP` → `WF_ADMIN_GROUP`, `WORKFLOW_TRANS_MSG_MAX_LEN` → `WF_TRANS_MSG_MAX_LEN`, `WORKFLANGO_ALLOW_IMPERSONATE` → `WF_ALLOW_IMPERSONATE`, `WORKFLANGO_SNAPSHOT_ENABLED` → `WF_SNAPSHOT_ENABLED`, `WORKFLANGO_ACCESS_DENIED_URL` → `WF_ACCESS_DENIED_URL`, `WORKFLANGO_NOTIFY_FUNC` → `WF_NOTIFY_FUNC`. `WF_HISTORY_TRANS_TYPE` (added this cycle) already had the correct prefix. **Breaking for projects upgrading from `1.0.0rc1`**: update `settings.py` before restarting.

### Fixed

- `WorkflowViewSetMixin.check_wf_permission` (DRF) did not pass `impersonated_by` to `is_owner()`, so any state created during an impersonation session (`State.impersonated_by != None`) raised `PermissionDenied` for two valid callers: the admin-impersonating-owner session that created it, and the real owner reclaiming it afterwards without impersonation. `check_wf_permission` now reads `impersonated_by` from `self.request` and passes it to `is_owner()`; a second guard (`state.owner == acting_user`) lets the real owner through when `is_owner()` returns False due to impersonation-context mismatch, so `transition_allowed()`'s existing `reclaiming_own_identity` logic can do its job. Three regression tests added to `tests/tests.py` (`CheckWfPermissionImpersonationRegressionTest`)
- `SebastianWorkflowSerializerMixin.datetime_format` renamed to `wf_datetime_format` to avoid clashing with `GUISerializerMixin.datetime_format` (drf-sebastian) which is a strftime pattern used in `_render_datetime()`. When both mixins were combined (the typical usage), `datetime_format = 'SHORT_DATETIME_FORMAT'` propagated to sebastian's `_render_datetime()`, which called `dt.strftime('SHORT_DATETIME_FORMAT')` — returning the literal string instead of a formatted date, since the value contains no `%` codes. The workflango attribute is now `wf_datetime_format` (a Django format-variable name resolved via `django.utils.formats.date_format`); consuming projects that overrode `datetime_format` on `SebastianWorkflowSerializerMixin` subclasses to change the state-badge date format must rename the override to `wf_datetime_format`

## [1.0.0rc1] - 2026-08-27

First release candidate. Feature-complete and used in production (as the `workflow` app inside WebGPV, at Comune di Milano since 2014); this candidate exists to get more real-world mileage as a standalone package before committing to the API-stability guarantee of a full `1.0.0`.

### Added

- Full Django i18n support for the library's own GUI chrome, with a bundled Italian translation catalog. `{% wtrans %}` (template) and `wgettext()`/`wgettext_lazy()` (Python) wrap the required `msgctxt "workflango"` so call sites don't need to write it by hand — see README.md "Internationalization (i18n)" for the maintainer workflow, including the `_translatable_strings.py` extraction registry `makemessages` needs
- `WorkflowModel.view_base_name`, `get_edit_url()`, `get_history_url()`, `get_change_state_url(destination)` — a single, formalized URL-naming convention (`<view_base_name>_list/_detail/_edit/_history/_change_state`) that the shipped templates and `GUITestMixin`'s view helpers now consistently rely on, replacing an unreconciled mix of an ad hoc `get_absolute_url()` derivation and an undocumented `view_base_name` attribute `GUITestMixin` already assumed existed
- Demo project (`testproject/`, English throughout): a traditional Django project (plain class-based views, no REST framework) driving two related models with group-based permissions — `Supplier` (`proposed` → `active` → `archived`, activation/archival gated to a `MANAGERS` group) and `Request` (`draft` → `submitted` → `approved`/`rejected`, restricted to targeting active suppliers only), plus a phase-conditional edit-form template pattern standing in for the field-level permissions workflango's group-based model doesn't have. Role-based demo accounts (`create_demo_data` management command, also seeding a few sample suppliers/requests) and GUI/workflow smoke tests (`testproject/demo/tests.py`) using `GUITestMixin`
- Demo GUI for the library's impersonation feature, superuser-only: `demo/middleware.py`'s `ImpersonateMiddleware` swaps `request.user` for a session-selected target (`ImpersonateStartView`/`ImpersonateStopView`, `demo/forms.py`'s `ImpersonateForm`) and stashes the real admin on `request.impersonated_by` — exactly the contract `_BaseWorkflowTransitionMixin.check_and_transition()` already expected, so transitions performed while impersonating record `State.impersonated_by` correctly with no library changes. Navbar shows the real admin's name with the impersonated target in parentheses, or a start link when not impersonating
- Full API reference generated with `pdoc` (`docs/api/`, regenerate with `tools/gen-docs.py`)

### Changed

- README rewritten with a "Django GUI" section documenting the view/URL conventions, an "Internationalization" section, and a "Demo project" section with the accounts table
- `workflango/templates/workflango/django/*.html` — every hardcoded Italian string wrapped for translation; every string in `TRANS_TYPE_MAP`, `views.py`'s `command_captions`, `views_mixins.py`'s runtime/access-denied messages, `forms.py`, `filters.py`, `filtersets.py`, and `wf_transition.py`'s transition-caption fallback converted from hardcoded Italian to English source strings wrapped with `wgettext()`/`wgettext_lazy()`
- Management commands' `help` text and `drf.py`'s `PermissionDenied` messages and sebastian GUI field/action labels (previously hardcoded Italian, never reaching any translation catalog) translated to English source strings, the latter now also wrapped for translation
- Demo `Supplier`/`Request` `workflow_defaults` now grant `read` broadly (`USERS` and `MANAGERS`) regardless of phase — only `edit`/`admin` (who can transition an object) stay narrowed per phase. Previously `read` defaulted to empty and only ever came as a side effect of also holding `edit`/`admin` *at that specific phase*, so e.g. a plain user could never view a supplier once it reached `active`/`archived`, and a manager couldn't view one they'd just archived (`archived` has no `edit`/`admin` group at all)
- `drf.py`'s direct coupling to sibling project [drf-sebastian](https://github.com/sigfrido/drf-sebastian) — the `gui_field`-decorated list column, `__can_update`/`to_representation()`, `template_namespace`, `can_update()`/`can_delete()`, `get_workflow_transitions()`, and the `history`/`change_state_form` actions — moved out into a new optional module, `workflango.contrib.sebastian` (`SebastianWorkflowSerializerMixin`/`SebastianWorkflowViewSetMixin`), never imported by core workflango. `workflango.drf` no longer imports or references sebastian at all; a consumer using drf-sebastian as their GUI layer now opts in explicitly via `workflango.contrib.sebastian` instead of getting it bundled unconditionally. **Breaking for consumers relying on the old bundled behavior** (e.g. SELCO) — see [docs/sebastian-integration.md](docs/sebastian-integration.md) for the drop-in replacement mixins

### Fixed

- `workflango/templates/workflango/django/*.html` never actually rendered since the WebGPV→workflango rename: `{% load bootstrap %}` / `{% load dashboard_tags %}` / `{% filter gpvref %}` (none exist in workflango) and context variables `workflow_view`/`edit_view`/`history_view`/`help_page` that nothing in the library ever set. `ChangeStateView.template_name` / `ObjectHistoryView.template_name` also pointed at `workflow/...` paths that didn't match the templates' real location under `workflango/django/...`
- `ChangeStateView` crashed with `AttributeError: 'NoneType' object has no attribute 'get_absolute_url'` on every successful transition when no `success_url` was set: `ModelFormMixin.form_valid()` sets `self.object = form.save()`, and `ChangeStateForm.save()` is a no-op returning `None`, so the default `get_success_url()`'s `self.object.get_absolute_url()` crashed before `_BaseWorkflowTransitionMixin`'s own `self.object` recovery ever ran. `ChangeStateView.get_success_url()` now uses `get_object()` (cached) instead of the transient `self.object`
- Demo `Request` detail/edit/change-state/history pages showed no transition buttons and an edit-button caption of the literal text "None": naming a model `Request` collides with Django's default `context_object_name` (the lowercased model name), so `SingleObjectMixin` was overwriting the real `HttpRequest` in the template context with the `Request` *instance* — every `{% if request.user == ... %}` in the shipped workflow templates silently came up false. Fixed with an explicit `context_object_name` on the affected demo views (`_RequestObjectNameMixin`); the missing `edit_button_label` (a separate, unrelated bug) is now set in both demo models' `workflow_defaults`
- Demo `Request`'s `draft` phase granted `MANAGERS` no `admin` rights (unlike `Supplier`'s parallel `proposed` phase, which does), so a manager viewing a draft request they didn't own never saw a "Take ownership (ADMIN)" button — an asymmetry in the demo config, not a library bug
- **[GitHub issue #1](https://github.com/sigfrido/workflango/issues/1)** — impersonation was audited only as a side-effect of an actual `transition()` call (`State.impersonated_by`), but every ownership check (`is_owner()`, and the inline equivalent inside `transition_allowed()`) compared only `state.owner == user`. Since the library's documented contract has consumers swap `request.user` to the impersonated target, an admin impersonating userx satisfied every ownership check exactly as if they *were* userx — with no forced audit trail and no distinction from userx acting for themselves. Worse, plain field edits (`WorkflowModelUpdate`) never create a `State` row at all, so an impersonated plain edit left zero trace. New `State.owned_by(user, impersonated_by=None)` requires both the raw owner match *and* an impersonation-context match; `is_owner()`, `take_ownership()`, `can_take_ownership()`, and `transition_allowed()` (which now also receives `impersonated_by` at all — it previously didn't, so no fix to the above could ever have taken effect) all route through it. An admin impersonating a user (or that user reclaiming back afterwards) must now go through an explicit, audited `take_ownership()` call before `is_owner()`-gated actions succeed — via a new `user == new_owner == current_owner` ("reclaiming own identity") rule in `transition_allowed()`'s reassignment check, which works identically regardless of group membership on either side, so it doesn't depend on the impersonated target being a manager. Also fixes a related `take_ownership()` bug where reclaiming a record already recorded as owned by the target silently no-opped, dropping the passed `impersonated_by` even when explicitly given. Two new `State.transition_type` values, `impersonate` and `reclaim`, make the hand-off explicit in the history instead of being mislabeled `resume`; a different, separately-authorized impersonator taking over an existing claim (e.g. a second admin) is by design (both claims independently audited as `impersonate`) — workflango deliberately doesn't gate *who* may impersonate *whom*, only that the currently-acting identity matches what's recorded, see README.md "Impersonation" / "Ownership and impersonation"
- `workflow_buttons.html` (and five other shipped templates) still gated action buttons with a raw `state.owner == request.user` comparison, unlike the `wf_editable`/`allowed_transitions` context variables the fix above already made impersonation-aware — so Release/Suspend/Delegate (and a few purely cosmetic bits: the "Me" label, unread-button visibility, list-view highlighting) kept rendering for an admin impersonating the owner *before* their explicit reclaim, even though clicking them correctly failed at `transition_allowed()` time. New `{% load workflow_tags %}` filter `owned_by` (`{% if state|owned_by:request %}`) wraps `State.owned_by()` for template use; every such comparison across the shipped templates now goes through it
- **[GitHub issue #2](https://github.com/sigfrido/workflango/issues/2)** — three date/datetime formatting call sites hardcoded Italian-style `DD/MM/YYYY` regardless of the active locale, a holdover from before this release's i18n work: `SebastianWorkflowSerializerMixin.datetime_format` (a raw `%d/%m/%Y %H:%M` strftime literal), `WorkflowFilterForm.search_data_min`/`search_data_max`'s `input_formats`, and `filters.datestr_local2iso()`'s accepted formats. All three now go through `django.utils.formats` instead, so the accepted/displayed format follows the active locale (verified: under `it` the output is unchanged from before, e.g. `"28/08/2026 15:45"`; under `en` it correctly becomes `"08/28/2026 3:45 p.m."` instead of staying Italian). `datetime_format` is now a Django format-variable *name* (default `'SHORT_DATETIME_FORMAT'`), not a strftime pattern — overriding it requires Django's own format-string syntax (e.g. `'d/m/Y H:i'`), not Python's `%d/%m/%Y`. Incidentally fixed a real, locale-independent bug found along the way: `search_data_min`/`search_data_max`'s `DateInput` widget had `type: 'date'` (an HTML5 native date input, which requires its `value` in ISO `YYYY-MM-DD` regardless of display locale) paired with `format='%d/%m/%Y'`, which could prevent the native date picker from correctly pre-filling a bound form's value — now hardcoded to the correct `'%Y-%m-%d'`
